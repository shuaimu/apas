# Task 8.4 — staging exercise (in progress)

Rig: local apas-server on 127.0.0.1:8099 with its own data dir; project CLI run
with APAS_CONFIG_DIR pointing at a throwaway config, so nothing touches the
user's real state or the production server. Providers are a stub script
(long-lived pty process emitting STUB-TICK) reached via claude_path/codex_path/
opencode_path in the rig config — this exercises process lifecycle without
spending agent quota. Project seeded with two panes: 501 terminal (host-backed)
and 502 structured agent.

## Defect found while setting up
/run/user/3000/apas/ph holds 68 project directories; only 4 contain a live
runtime. 64 are completely empty. terminate_tmux_host removes the per-pane
directory (socket_path.parent()) but never the project directory above it, so
an empty skeleton is left behind for every project that ever hosted a pane.
Harmless in size (tmpfs, empty dirs) but unbounded, and it actively obscured
real state during this audit.

## Scenario: unexpected CLI loss + adoption ("staging upgrade") — PASS
CLI killed without an authenticated shutdown, then a replacement CLI started.

  Immediately after the CLI died:
    agent provider (3305067)     gone      — CLI-owned child dies with its CLI
    terminal provider (3304414)  ALIVE     — retained by its pane host
    pane-host tmux               alive
  After the replacement CLI started:
    terminal provider pid        3304414   (unchanged — same process adopted)
    pane-host instance_id        54218267  (unchanged)
    controller_generation        1 -> 2    (a new controller took ownership)
    agent provider pid           3305067 -> 3479557 (restarted, as specified)

This is the preservation claim proved on live processes: the terminal agent
survived CLI replacement with its identity intact, the structured pane restarted,
and the generation counter shows a genuine authenticated handoff rather than a
stale read of an old descriptor.

## Scenario: project deletion — PASS
POST /projects/<id>/delete.

  Unconfirmed request rejected: 422, "missing field `confirmation`"; the handler
  additionally requires confirmation == project_id. Deletion cannot be triggered
  by an accidental or replayed request.
  Confirmed request: 202 {"success":true,"status":"deleting"}
  daemon: "stopped persistent pane hosts ... " (second occurrence, 04:10:32)
  after:  cli dead, runtimes 0, tmux sessions 0, no provider survived

  Note: the host-local project registry entry (projects.json) survives server-side
  deletion. Expected — that registry is host-local state — but worth knowing when
  reconciling a deleted project against a machine that still lists it.

## Rig isolation note
A second daemon cannot run on a host that already has one: daemon_state_path()
is runtime_dir()/daemon.json and runtime_dir() is machine-scoped, so
APAS_CONFIG_DIR alone does not isolate it. Overriding XDG_RUNTIME_DIR as well
made the rig hermetic (its own daemon.json AND its own pane-host runtime root)
without touching the production daemon. Worth recording for anyone repeating
this exercise.

## Still not exercised
Failed update preparation. Proving "no false reboot success" needs

## Scenario: failed update preparation — PASS
Staged honestly rather than simulated. The rig CLI was launched from a copy of
the real binary ($RIG/bin/apas-rig), so LAUNCH_BINARY_PATH — which
resolve_preferred_apas_executable() prefers — pointed at a file under rig
control. That file was then replaced (by rename, since a running executable
cannot be written in place) with a script that exits non-zero on `--version`,
reproducing a corrupt or partially-installed update. The spec scenario names
"fetch, build, validate, or install"; this exercises the validate step in
prepare_cli_restart().

Reported phase sequence, over the real web WebSocket:
    accepted
    preparing   "Preparing CLI replacement"
    failed      "CLI reboot preparation failed; current CLI and panes remain
                 running: prepared executable failed its version probe"

State afterwards:
    cli pid          3511852  (alive, unchanged)
    provider pids    3512196 3512350 3512376  (unchanged from baseline)
    pane-host runtime present
    handoff marker   none written — no detach was staged
    CLI log          "CLI reboot preparation failed without detaching panes"

No false reboot success was reported, and no pane process was disturbed.

## Two notes on driving this by hand
- A raw web client must advertise the same capabilities the real web sends
  (project_policy_v1, pane_work_summary_v1, cli_lifecycle_v1). Without
  project_policy_v1 the server answers with a policy error rather than routing
  the request; a test client that ignores non-lifecycle messages will look like
  it was silently dropped when it was not.
- Sending a lifecycle request before the CLI has finished registering yields
  "This project CLI is too old for safe lifecycle controls" — correct behaviour
  for a session with no capabilities recorded yet, but easy to misread as a
  product defect. Wait for "CLI client registered" before driving.
